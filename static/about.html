About this project

From notebook to deployed API.

This app takes a brain MRI, classifies it as glioma, meningioma, pituitary, or no tumor, and shows a Grad-CAM heatmap of what the model actually looked at. Here's why it exists, how the pipeline works, the real bugs and a production incident it took to get the accuracy numbers on this page trustworthy, and what's still left to fix.

01Origin

Why this exists

The model started as a Jupyter notebook: a small CNN trained on brain MRI scans to tell four classes apart, run cell-by-cell on a personal machine until it hit a respectable test accuracy. That's useful for validating an approach, but a notebook on its own has no API, no deployment, and no failure handling — nobody can open a link and try it.

This project turns that notebook into something a recruiter, another developer, or anyone with a browser can actually use: a FastAPI backend serving real-time inference, a Grad-CAM layer so the prediction isn't a black box, and a deployment pipeline where pushing to main is the only way the live app changes.

Getting there turned out to be a much longer road than "wire up an API." Along the way this surfaced a real production incident, a subtle GPU-vs-CPU numerics bug, and a genuine, still-open accuracy weak point — all covered in detail further down this page.

02The model

How it works

The network uses four Conv2D + MaxPooling blocks (64 / 64 / 128 / 512 filters). The last block feeds both Global Average Pooling and Global Max Pooling in parallel, concatenated together into a Dense(128) layer with 0.3 dropout, ending in a 4-way softmax. Trained on the Kaggle brain-tumor-mri-dataset at 256×256 resolution. Nothing exotic — the point of this build was never a state-of-the-art architecture, it was proving the surrounding engineering.

  1. Decode & resizeThe uploaded image is decoded and resized using TensorFlow's own ops — not PIL. The model was trained on TF's internal resize behavior, and a PIL reimplementation uses different interpolation, which quietly skews accuracy between training and serving.
  2. NormalizePixels are rescaled to a 0–1 float range, matching training preprocessing exactly.
  3. PredictThe CNN, loaded once at process startup, returns a class label plus a confidence score for all four classes — not just the top guess.
  4. ExplainGrad-CAM finds the model's last convolutional layer programmatically (never a hardcoded layer name), traces gradients back through it, and overlays a heatmap so you can see what drove the call.

The training notebook doesn't fix a random seed for weight initialization (only the train/validation split is seeded), so accuracy varies a little between runs. These numbers are also deliberately not the ones the training notebook first reported — they're re-measured directly against the exact code path production actually runs (CPU inference, the real app.preprocessing → app.inference pipeline), because it turned out the notebook's own numbers were quietly inflated by a GPU-specific bug. 03Issues I ran into

What went wrong

A metric that was measured on the wrong backend. The training notebook first reported 99.53% / 96.70% / 92.44% (train/val/test) — run on a GPU (Apple Silicon, tensorflow-metal) during local development. Re-measuring the exact same weights on CPU (the only backend Cloud Run actually has — there's no GPU option there at all) gave a materially worse 88.06% test accuracy, with 154 of 1,600 test images flipping predicted class purely based on which backend ran inference. Bisecting that gap layer-by-layer found the exact cause: model.predict() on the Metal GPU backend silently skips the ReLU activation on a Dense layer under compiled-graph execution, passing raw (partly negative) values into the final softmax and corrupting the output. Forcing eager execution fixed it immediately, which confirmed the bug lives in Metal's compiled-graph path, not the model itself — and matches a known, still-unresolved upstream TensorFlow issue. Lesson: never trust a GPU-measured metric for a model that will only ever serve on CPU in production — every accuracy number on this page is now CPU-verified against the real serving path.

A class the model still confuses. Meningioma is the real accuracy weak point (67.25% recall, mostly misread as glioma). Grad-CAM inspection pointed at a location-cue problem: the correctly-classified meningioma heatmaps skew toward the skull-adjacent periphery, while gliomas sit deeper and more centrally — and this architecture's GlobalAveragePooling/GlobalMaxPooling layers can't encode where a signal is, only that it exists. That's likely compounded by RandomErasing, a training-time augmentation that randomly blanks a small rectangular region per image — a fixed-size erasure box has proportionally higher odds of fully wiping a thin peripheral meningioma than a large central glioma mass. Three fine-tuning attempts followed (shrinking the erasure area, upweighting meningioma/glioma loss, and both together) — none produced a real, CPU-verified improvement, and the loss-weighting change actively made things worse. A real fix looks like it needs an architectural change (a non-pooled spatial feature), not a training-time tweak, and hasn't been attempted yet.

It performs worse on MRIs that don't match the training data's "house style." Scans pulled from random sources on the internet — different scanners, different windowing/contrast conventions, different framing — are classified noticeably less reliably than the Kaggle test set, even for cases that look unambiguous to the eye. This isn't really a bug so much as an honest limitation of the training data: the source dataset merges three separate collections, each with its own acquisition and preprocessing quirks, and the model has learned some of that as signal rather than noise. My take: if this were being built for an actual hospital or imaging provider, trained and validated on that institution's own scanner output and protocols, I'd expect it to perform well — but a single model that generalizes well across every MRI machine, protocol, and institution in the world is close to an unsolvable problem with this amount of data. Real clinical deployments are institution-specific for exactly this reason.

A production incident: the live app was silently serving the wrong model. A user report of "every single prediction wrong" led to discovering that the pinned Hugging Face Hub revision in app/config.py, despite a commit message reading "Retrain: train 99.53% / val 96.70% / test 92.44%," actually contained the pre-retrain model file, verified by SHA-256. The original upload script had pushed the wrong local path to the Hub — twice — under a commit message describing the right model. This went uncaught for a while because a correct model file happened to already be sitting in a local dev machine's cache, masking what a fresh scripts/download_model.py run (what Docker build time, and therefore Cloud Run, actually does) would pull. Real production impact was severe: as low as ~42% accuracy with 0% glioma recall, confirmed by sending real images to the live endpoint. The fix was re-uploading the verified-correct file under a new, hash-checked commit and re-pinning the revision — and the lesson driving the "what's next" item below: a commit message is a claim, not a guarantee; only a hash (or a smoke test) proves what's actually being served.

04Roadmap

What's next

  1. Post-deploy smoke test in CIHit a known-label fixture image against every freshly deployed revision and assert the predicted class, so a wrong-model-file incident like the one above gets caught automatically before a real user does.
  2. A non-pooled spatial featureGive the architecture some way to encode tumor location instead of collapsing everything through global pooling — the most promising lead for closing the meningioma/glioma gap, not yet attempted.
  3. Transfer learningSwap the from-scratch CNN for a pretrained backbone (EfficientNet/ResNet-style) to raise the overall accuracy ceiling beyond what's reachable from ~5,700 training images alone.
  4. Audit the train/test splitThe source dataset merges three separate collections — worth checking for duplicate or near-duplicate scans across the split before trusting these numbers as a hard ceiling.
  5. Fixed random seed for trainingWeight initialization currently isn't seeded, so accuracy shifts a little between retraining runs — pinning it would make future before/after comparisons trustworthy.
05Under the hood

Architecture

The backend is split into small, independently testable modules rather than one monolithic route handler: preprocessing (bytes in, normalized array out), inference (array in, prediction out), and Grad-CAM (array in, heatmap out). The FastAPI route layer just wires them together and translates failures into clean HTTP errors — a bad upload returns a 400, never an unhandled crash.

The trained .keras file itself never touches git. It's hosted on a public Hugging Face Hub model repo and pulled into the Docker image at build time, pinned to a specific commit revision — so an unrelated code change can never silently swap the live model, and the running container has zero runtime dependency on Hub availability.

06Deployment

Switching from Hugging Face Spaces to Cloud Run

The original plan was Hugging Face Spaces on its free Docker SDK tier — a natural fit, since the model was already going to live on the HF Hub. Mid-build, Hugging Face changed policy to require a PRO subscription to create a Docker SDK Space on a personal account, even on free CPU hardware. Paying a subscription fee for a portfolio demo didn't make sense, so the deploy target moved.

Google Cloud Run ended up a better fit anyway: it runs the exact same Dockerfile unmodified, its free tier's memory ceiling is well above what TensorFlow needs (this app runs at 2 GiB / 2 vCPU), and it scales to zero when nobody's using it. The only cost is a GCP billing account on file — no recurring charge at this app's traffic level.

GitHub stays the single source of truth throughout: a GitHub Actions workflow builds the image, pushes it to Artifact Registry, and deploys a new Cloud Run revision on every push to main. Nothing gets deployed by hand.
